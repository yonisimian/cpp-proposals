## Abstract

This proposal introduces an extension to C++ structured bindings, allowing assignment to existing variables.

## Motivation

Structured bindings (`auto [x, y] = foo();`) can only declare new variables. Assigning to pre-existing variables requires `std::tie` from `<tuple>`. There is no single construct that does both.

This proposal closes that gap, with several advantages over std::tie:

1. **Mixed-mode** — Neither `std::tie` nor structured bindings alone allow some elements to be new variables and others pre-existing in the same statement. P3817 uniquely enables this:

   ```cpp
   int id;
   auto [using id, name] = get_record();  // id is assigned; name is declared
   ```

<sub>[[‡ 1]](#ex-1)</sub>

2. **Unified syntax** — One construct for both assignment and initialization reduces cognitive overhead and produces more consistent code. Currently, initialization uses structured bindings; reassignment uses `std::tie`.

3. **Standard library use may be restricted, even where available** — Some C++ environments prohibit standard library use by policy, regardless of whether `<tuple>` is technically present.<br>
`std::tie` is unusable there; a language-level feature is usable.

   For example, Fuchsia's Zircon kernel disallows standard library use in-kernel [[CxxInZircon]](#references).<br>
   [[PageFault]](#references) assigns a loop-scoped variable from a structured binding to an out-of-loop variable today:

   ```cpp
   auto [fault_status, _] =
       mapping->PageFaultLocked(guest_paddr, pf_flags, 0, &page_request);
   status = fault_status;
   ```

   With P3817, this becomes one statement:

   ```cpp
   auto [using status, _] =
       mapping->PageFaultLocked(guest_paddr, pf_flags, 0, &page_request);
   ```

<sub>[[‡ 2]](#ex-2)</sub>

4. **Encouraged by [[P0144R2]](#references)** — The authors of the original structured bindings paper explicitly invited this extension [section 3.3]:

   > "This can always be proposed separately later as a pure extension if desired."

## Proposal

Extend structured binding syntax to allow the `using` keyword before an element in the _sb-identifier-list_ to denote assignment to an already-existing modifiable lvalue, rather than declaration of a new variable.

### Syntax

The grammar splits _sb-identifier_ into two named alternatives, so that the wording can name the kind of element it means:

<pre>sb-identifier:
    sb-declaring-identifier
    sb-assigning-identifier

sb-declaring-identifier:
    ...<sub>opt</sub> identifier attribute-specifier-seq<sub>opt</sub>

sb-assigning-identifier:
    using unary-expression ...<sub>opt</sub></pre>

The _sb-declaring-identifier_ is the existing declaration form, unchanged. The _sb-assigning-identifier_ is new: `using` followed by a _unary-expression_ that shall designate a modifiable lvalue, optionally followed by `...`. No _attribute-specifier-seq_ appears in this form: attributes appertain to a newly declared variable, and no variable is introduced here.

The two forms place the ellipsis differently on purpose: the declaring one _declares_ a pack, the assigning one _expands_ an existing one. C++ spells a declared pack's ellipsis on either side of the name (`Ts... args`, `T ...args`, `...rest`), but spells every pack expansion after its pattern (`f(args...)`); each form follows the convention of the operation it performs. The two never compete for the same token, since in the assigning form the ellipsis follows an _expression_.

When the assigning form carries `...`, the _sb-identifier_ is a pack expansion ([[temp.variadic]](https://eel.is/c++draft/temp.variadic)) whose pattern is the _unary-expression_. The unexpanded pack may appear anywhere within that pattern — as the pattern itself (`targets`) or nested inside it (`arr[Is]`), exactly as in any other pack expansion — and each element of the structured binding is assigned from the corresponding element of _e_ to the corresponding element of that expansion.

### Semantics

**`operator=`** The hidden variable _e_ is introduced exactly as today (per [[dcl.struct.bind] ¶1](https://eel.is/c++draft/dcl.struct.bind)). The difference lies in how each element SBᵢ is resolved: for a `using`-marked element, instead of introducing a new name, the implementation assigns from the corresponding element of _e_ to the existing variable via `operator=`.

**Order of assignment.** For all three decomposition kinds (tuple-like, array, and otherwise/aggregate), the elements SB₀, …, SBₙ₋₁ are resolved in that lexical order: SBᵢ — its assignment if `using`-marked, its reference-binding otherwise — is fully completed before SBᵢ₊₁ is evaluated. In particular, for a `using`-marked SBᵢ, the assignment reads its right-hand element from _e_ and writes it via `operator=` before any later SBⱼ (j > i) is evaluated.

_Rationale:_ tuple-like decomposition already has this ordering "for free" from [[dcl.struct.bind] ¶7](https://eel.is/c++draft/dcl.struct.bind#7), since each SBᵢ there is a separately-initialized variable, sequenced by ordinary declaration semantics. Array and aggregate decomposition never needed an order, since without `using` every SBᵢ is a side-effect-free reference binding. `using` adds `operator=` side effects, making the order observable: `auto& [_, using arr[0], using arr[1]] = arr;` intends an evict-and-shift, but silently corrupts `arr` under the other order. This rule generalizes the existing tuple-like guarantee to the two forms that previously had none.

The _ref-qualifier_ determines the type of _e_, which in turn determines whether the assignment is a copy or a move — no special-casing is required:

> <sup>†</sup> [[dcl.struct.bind] ¶8](https://eel.is/c++draft/dcl.struct.bind) imposes no aggregate requirement: any class type with publicly accessible direct members and no `std::tuple_size` specialization reaches this case, including non-aggregates with user-provided constructors.

**Immediate-move implication.** For `auto [using x, ...]`, the move assignment to `x` happens at the binding statement, consuming that element of _e_. A non-`using` element does not move — it binds a reference into _e_ — so moving out of one always takes an explicit `std::move`. Where the assignment copies rather than moves, nothing is consumed.

### Specifiers

Specifiers appertain to the hidden object _e_, never to the `using`-marked targets. [[dcl.struct.bind] ¶1](https://eel.is/c++draft/dcl.struct.bind) defines _S_ as the declaration's `constexpr`, `constinit` and storage-class specifiers, and _e_ is defined using _S_ together with the declaration's cv-qualifiers. A `using`-marked element introduces no new entity — it assigns from the corresponding element of _e_ to an existing variable, whose type this declaration cannot change. Every specifier therefore keeps the meaning it has for an ordinary structured binding, and none of them is ill-formed:

- `const` qualifies _e_, and `constexpr` — valid on structured binding declarations since C++26, [[P2686R5]](#references) — implies it. The elements read from _e_ are const, so the assignment to a `using`-marked target copies rather than moves.
- `static` and `thread_local` give _e_ static or thread storage duration. _e_ is initialized once; every later execution of the statement assigns from that same _e_ — which earlier iterations may have moved from.
- `constinit` constrains the initialization of _e_, and `volatile` qualifies it. Neither changes what a `using`-marked element does.

### Further Design Decisions

#### Returned Modifiable Lvalues

The `using` specifier may also appear before an expression yielding a modifiable lvalue, not just a plain identifier. This is the language-level equivalent of `std::tie` with non-variable arguments:

```cpp
// std::tie equivalent
std::tie(foo(), s[0]) = get_pair();

// with P3817
auto [using foo(), using s[0]] = get_pair();
```

<sub>[[‡ 17]](#ex-17)</sub>

#### C++26 `_` Placeholder

P3817 composes naturally with C++26's `_` placeholder for discarding elements:

```cpp
int x;
auto [using x, _] = get_pair();  // assign first element to x, discard second
```

<sub>[[‡ 18]](#ex-18)</sub>

Note: `using _` is ill-formed — `_` is a discard placeholder and cannot be the target of an assignment, even where `_` names an ordinary variable rather than a placeholder.

This provides a complete, library-free replacement for `std::tie` with `std::ignore`:

#### Duplicate Targets

A binding list may assign to the same object more than once. The order rule makes the result well-defined — the last assignment wins.

A rule forbidding it was considered and dropped: assigning twice is not a mistake, only pointless, and no test can enforce it — a test on the spelling misses two names for one object, and a test on the objects themselves is undecidable, since `using f(), using g()` may return the same object:

```cpp
int var;
int& x = var;
int& y = var;
auto [using x, using y] = foo();  // x and y designate the same object
```

#### Reusing a Declared Name as a Target

An assignment target may share its name with a binding the declaration introduces. The operand finds whatever the name means outside the list, since the bindings are not in scope inside it:

```cpp
struct Counter {
    int count = 0;                                  // the member

    std::pair<int, int> tick();                     // {delta, running_total}

    int step() {
        auto [count, using count] = tick();
        //    │             │
        //    │             └── this `count` is the MEMBER: at this point the
        //    │                 binding declared to its left is not yet in scope
        //    └── declares a local binding named `count`

        use(count);          // the binding — first element (delta)
        return this->count;  // the member  — second element (running_total)
    }
};
```

The two cases that would warrant a rule are already ill-formed: redeclaring a name that exists in the same scope, and naming a binding that is not yet in scope — which is simply an undeclared identifier. What is left is the deliberate reuse above, whose meaning follows from the ordinary scope rules and whose behaviour is well-defined, so forbidding it is unnecessary.

#### Packs

P3817 composes naturally with C++26 structured binding packs [[P1061R10]](#references).

**Non-pack `using` alongside a regular pack** requires no special treatment — the two are orthogonal:

```cpp
int x;
auto [using x, ...rest]  = get_tuple();  // x is assigned; rest is a new binding pack
auto [...rest, using x]  = get_tuple();  // rest is a new binding pack; x is assigned last
```

<sub>[[‡ 21]](#ex-21)</sub>

**`using expr...`** — when `...` follows the _unary-expression_, the _sb-identifier_ is a pack expansion whose pattern is that expression. Each element of the structured binding is assigned from the corresponding element of _e_ to the corresponding element of the expansion, following the same ref-qualifier rules as non-pack `using`. No new name is introduced:

```cpp
template <typename... Ts>
void assign_from(std::tuple<Ts...> t, Ts&... targets) {
    auto [using targets...] = std::move(t);  // each tuple element moved into the corresponding target
}
```

<sub>[[‡ 22]](#ex-22)</sub>

Mixed usage is also valid:

```cpp
template <typename T, typename... Rest>
void assign_all(T& head, Rest&... tail, std::tuple<T, Rest...> t) {
    auto [using head, using tail...] = std::move(t);
}
```

<sub>[[‡ 23]](#ex-23)</sub>

The operand may be any expression, not only a name — an unexpanded pack may appear nested inside it, as in any other pack expansion:

```cpp
template <typename... Ts, std::size_t... Is>
void assign_into(std::tuple<Ts...> t, std::array<std::common_type_t<Ts...>, sizeof...(Is)>& arr,
                 std::index_sequence<Is...>) {
    auto [using arr[Is]...] = std::move(t);  // each tuple element moved into the corresponding arr[Is]
}
```

<sub>[[‡ 24]](#ex-24)</sub>

**More than one expansion** is allowed — any number of `using` expansions may appear in one binding list, and a declaring pack may appear alongside them. Nothing is left to infer: each expansion's length is fixed by the pack named in its pattern, so only a declaring pack's size comes out as the remainder, and the C++26 rule that a declaration contains at most one declaring pack ([[P1061R10]](#references)) is what keeps that remainder well-defined.

```cpp
auto [using a..., using b...] = get_tuple();  // |a| + |b| must be the number of elements of the tuple
```

The existing constraints extend naturally:

- `using _...` is ill-formed — `_` is a discard placeholder.
- Taken together, the pack expansions must produce exactly the structured binding size of _E_ less the number of non-pack elements; otherwise the program is ill-formed.

##### Current Alternatives

Assigning from a tuple-like type to a pack of existing variables without P3817 requires either the standard library or significant boilerplate:

```cpp
template <typename... Ts>
void assign_from(std::tuple<Ts...> t, Ts&... targets) {
    // Option 1: std::tie — requires <tuple>
    std::tie(targets...) = std::move(t);

    // Option 2: index sequence — verbose
    [&]<std::size_t... Is>(std::index_sequence<Is...>) {
        int dummy[] = { (targets = std::get<Is>(std::move(t)), 0)... };
        (void)dummy;
    }(std::index_sequence_for<Ts...>{});
}
```

With P3817:

```cpp
template <typename... Ts>
void assign_from(std::tuple<Ts...> t, Ts&... targets) {
    auto [using targets...] = std::move(t);
}
```

## Examples

### Patterns

#### Loops

Because the structured binding declaration fires on every iteration, `using`-marked elements are reassigned each time. This enables tracking state across iterations without a separate assignment in the loop body:

```cpp
// Returns {head, tail} split at the first delimiter
std::pair<std::string_view, std::string_view>
split_first(std::string_view s, char delim);

std::string_view remaining = input;
while (!remaining.empty()) {
    auto [token, using remaining] = split_first(remaining, ' ');
    process(token);
}
```

<sub>[[‡ 26]](#ex-26)</sub>

Mixed-mode is equally natural — accumulate one variable while binding fresh names for the rest:

```cpp
struct Point { double x, y; };
std::vector<std::pair<Point, double>> trajectory;  // {position, timestamp}

Point last{};
for (auto [using last, _] : trajectory) { /* last updated each step */ }
// last is the final point of the trajectory
```

## Alternative Syntaxes Considered

### Option A: `&` Symbol

```cpp
int x;
auto [&x, y] = get_values();
```

**Pros:**

- Concise
- `&` suggests "referencing something that already exists"
- Familiar to developers comfortable with reference syntax

**Cons:**

- Ambiguous with address-of in expressions like `auto [&get_reference(), y] = ...`
- `]]` in `auto [&map[key], y]` resembles attribute syntax
- Visual similarity to `auto& [x, y]` may cause initial confusion

### Option B: `using` Keyword _(preferred by authors)_

```cpp
int x;
auto [using x, y] = get_values();
```

<sub>[[‡ 28]](#ex-28)</sub>

**Pros:**

- Unambiguous — no confusion with address-of or function pointers
- Clear semantic intent: "using" an existing variable rather than declaring a new one
- Works cleanly with returned modifiable lvalues: `auto [using get_reference(), y] = ...`
- Echoes the existing use of `using` to refer to a name declared elsewhere.

**Cons:**

- More verbose than `&`
- Introduces contextual keyword usage within structured bindings

### Other Syntaxes (Rejected)

- **`=x`** — Conflicts with lambda capture-by-value intuition (`[=]`).
- **`let`** — Conflicts with Pattern Matching proposals.
- **`tie x`** — Overly verbose; confusingly evokes `std::tie` even though it does not use it.
- **Implicit (no specifier)** — Would silently assign or shadow based on scope, violating the principle of least surprise.

## Wording

### Structured binding declarations: [dcl.struct.bind]

**[1]**

- "A structured binding declaration introduces the identifiers v<sub>0</sub>, v<sub>1</sub>, …, v<sub>N−1</sub> <s>of the sb-identifier-list</s> <u>of the _sb-declaring-identifiers_ in its _sb-identifier-list_</u> as names."
- <u>An _sb-declaring-identifier_ whose _identifier_ is preceded by an ellipsis, or an _sb-assigning-identifier_ whose _unary-expression_ is followed by an ellipsis, is a _pack sb-identifier_; the elements of a pack _sb-identifier_ are the elements of the structured binding pack it introduces, or of the pack expansion it expands, as applicable.</u>
- "<s>An sb-identifier that contains an ellipsis</s> <u>An _sb-declaring-identifier_ whose _identifier_ is preceded by an ellipsis</u> introduces a structured binding pack."
- "A structured binding is either <u>an _sb-declaring-identifier_</u> <s>an sb-identifier that does not contain an ellipsis</s> <u>whose _identifier_ is not preceded by an ellipsis</u> or an element of a structured binding pack."
- "The optional _attribute-specifier-seq_ of <s>an sb-identifier</s> <u>an _sb-declaring-identifier_</u> appertains to the associated structured bindings."
- "The type of the id-expression _e_ is called _E_. [Note 1: _E_ is never a reference type ([expr.prop]). — end note] <u>The id-expression _e_ is an lvalue if the type of the entity _e_ is an lvalue reference and an xvalue otherwise.</u>"

**[2]**

- "The structured binding size of _E_, as defined below, is the number of <s>structured bindings</s> <u>elements</u> that need to be <s>introduced</s> <u>resolved</u> by the structured binding declaration."
- "If there is no <s>structured binding pack</s> <u>pack _sb-identifier_</u>, then the number of elements in the _sb-identifier-list_ shall be equal to the structured binding size of _E_."
- "the number of elements <s>of the structured binding pack</s> <u>of the pack _sb-identifiers_</u> <s>is</s> <u>shall be equal to</u> the structured binding size of _E_ less the number of non-pack elements in the _sb-identifier-list_."

**[3]**

- "Let SBᵢ denote the i<sup>th</sup> <s>structured binding</s> <u>element</u> in the structured binding declaration after expanding the <s>structured binding pack</s> <u>pack _sb-identifiers_</u>, if any."
- <s>[Note 2: If there is no structured binding pack, then SBᵢ denotes vᵢ. — end note]</s>

**Insert after ¶3:**

<u>An _sb-assigning-identifier_ introduces no names and is not a structured binding. If it is not a pack _sb-identifier_, the object designated by its _unary-expression_ is its _assignment target_, and that _unary-expression_ shall be a modifiable lvalue. If it is a pack _sb-identifier_, the pattern designates one _assignment target_ per element of the expansion, and each of them shall be a modifiable lvalue.</u>

<u>For each SBᵢ that is not a structured binding, the assignment expression `target = element` is evaluated, where _target_ is the assignment target of SBᵢ and _element_ is the object or value that corresponds to SBᵢ — the element _i_ of the array in the array case, the _initializer_ in the tuple-like case, or `e.m`ᵢ in the member case.</u>

<u>An SBᵢ that is a structured binding is resolved by introducing it; any other SBᵢ is resolved by evaluating its assignment expression. The initialization of _e_, and any conversion of _e_ considered as a decision variable ([stmt.pre]), is sequenced before the resolution of SB₀, and the resolution of SBᵢ is sequenced before the resolution of SBᵢ₊₁.</u>

**Insert after ¶5:**

<u>If the _unary-expression_ of an _sb-assigning-identifier_ is the identifier `_`, the program is ill-formed.</u>

**[6]**, **[7]**, **[8]**

- ¶6: "Each SBᵢ <u>that is a structured binding</u> is the name of an lvalue that refers to the element i of the array and whose type is T; the referenced type is T."
- ¶7: <s>"In either case, _e_ is an lvalue if the type of the entity _e_ is an lvalue reference and an xvalue otherwise."</s> (moved to ¶1)
- ¶7: "<s>variables are introduced with unique names rᵢ as follows</s> <u>for each SBᵢ that is a structured binding, a variable is introduced with a unique name rᵢ as follows</u>" — before `S Uᵢ rᵢ = initializer ;` — and "Each SBᵢ <u>that is a structured binding</u> is the name of an lvalue of type Tᵢ that refers to the object bound to rᵢ; the referenced type is Tᵢ."
- ¶7: <s>"The initialization of _e_ and any conversion of _e_ considered as a decision variable ([stmt.pre]) is sequenced before the initialization of any rᵢ." "The initialization of each rᵢ is sequenced before the initialization of any rⱼ where i&lt;j."</s>
- ¶8: "each SBᵢ <u>that is a structured binding</u> is the name of an lvalue that refers to the member mᵢ of _e_ and whose type is that of `e.m`ᵢ; …"
